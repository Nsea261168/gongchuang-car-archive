# 工创赛智能救援车开发手册

> 给智能救援车队员阅读。工程服务于确定的比赛任务与硬件组合；开发前先阅读[智能救援小车最终骨架计划](智能救援小车最终骨架计划.md)，再将需求准确交给 AI。
> 项目创始人：超凡。

## 1. 先建立一个整体认识

工程代码从底到顶分为五部分：

| 目录 | 可以把它理解成 | 一般什么时候改 |
|---|---|---|
| `Core/` | STM32 和 CubeMX 生成的基础代码 | 修改芯片外设配置时 |
| `BSP/` | 这块控制板怎样使用 CAN、SPI、UART 等外设 | 修改板级通信和中断时 |
| `Drivers/` | 电机、IMU、雷达、舵机、LCD 等设备驱动 | 接入或修改设备时 |
| `Library/` | PID、姿态算法等纯软件算法 | 修改通用算法时 |
| `App/` | 上电流程、公共服务和应用任务 | 开发功能时主要修改这里 |

依赖关系只有一个方向：

```text
App → Drivers / Library → BSP → Core / HAL
```

简单说：Task 可以调用电机驱动，但电机驱动不能反过来知道自己属于哪个 Task。

## 2. 任务是怎样运行的

本工程没有为每个任务建立一个无限循环。`main.c` 中只有一个主循环，它会不停执行：

```text
系统维护 → 扫描按键 → 推进当前任务一步 → 回到开头
```

- 系统维护：更新 IMU、电机安全、状态灯和上电状态；
- 扫描按键：完成 ADC 读取、消抖并产生按键事件；
- 任务管理：显示菜单，或者调用当前 Task 执行一小步。

因此任何 Task 都不能长时间等待。一个任务卡住，按键、IMU 和安全检测都会一起卡住。

## 3. 每个任务只有三个阶段

```text
Enter（进入一次） → Tick（反复推进） → Exit（退出一次）
```

- `Enter`：重置任务状态、启动本任务需要的设备、显示初始界面；
- `Tick`：读取数据并推进状态机，每次执行后马上返回；
- `Exit`：停止电机、PWM、DMA 或其他设备，恢复安全状态。

当前任务安排（诊断与联调入口）：

| 任务 | 用途 |
|---|---|
| Task0 | LD06 雷达显示 |
| Task1 | IMU 姿态显示 |
| Task2 | 执行机构与电机方向标定示例 |
| Task3 | 五向按键 ADC 与事件诊断 |
| Task4～Task5 | 定位、视觉、底盘联调预留 |
| Task6 | UART7 松甲驱动板 / MG513P30 四轮闭环测试 |

菜单中使用上、下选择任务，右键进入；任务内按左键会安全退出并返回菜单。

## 4. 怎样让 AI 开发一个任务

开发功能时先确认它位于视觉、雷达、姿态、底盘、安全或任务状态机哪一层；不要绕过 H7 的最终 `vx / vy / wz` 安全门控。提问时说清下面五件事：

1. 使用哪个任务槽；
2. 输入是什么，例如按键、IMU、雷达或串口命令；
3. 输出是什么，例如电机速度、舵机角度或 LCD 内容；
4. 动作按什么顺序执行；
5. 什么情况下必须停止或退出。

可以直接复制下面这段：

```text
请先阅读 Docs/AI_DEVELOPMENT_GUIDE.md，并检查当前代码。
在【任务/服务】中实现【功能名称】。
输入：【传感器、按键或通信命令】。
输出：【电机、舵机、LCD 等】。
流程：【按顺序描述动作】。
安全要求：【限幅、超时、退出停机条件】。
保持现有分层和 Enter/Tick/Exit 调度，不使用阻塞延时。
完成后编译并告诉我还需要哪些硬件验证。
```

如果需求涉及新硬件，还要告诉 AI：设备型号、接线、使用的接口以及参考例程来源。

## 5. 烧录前只检查四件事

- AI 是否明确报告编译为 `0 Error(s)`；
- 是否说明了修改哪些文件以及任务入口在哪里；
- 电机或机构是否已经架空、限幅，并准备好安全退出；
- AI 提到的方向、零点和参数是否经过硬件确认。

“编译成功”“烧录成功”和“硬件验证成功”是三件不同的事，不要混为一谈。
