# DMstm32 工创赛智能救援车协作规则

> 本文件位于 `Docs/`，是工创赛智能救援车长期有效的工程硬规则。DMstm32 面向达妙 STM32H723 控制板，服务于本车的视觉、雷达、IMU、松甲底盘和任务调度。
> 项目创始人：超凡。

## 1. 项目定位

- 完成智能救援赛道中的物料搜索、接近、推送确认与安全移动；
- 以 H7 为唯一决策中心，统一视觉、雷达、IMU 和松甲底盘的数据边界；
- 在裸机协作式调度下保证通讯、控制和安全超时可预测；
- 保持工程独立可编译，并让 AI 的修改、编译、烧录和实机验证可分别核查。

本工程的电机、IMU、雷达、LCD 和输入任务服务于这台救援车。未验证的机械方向、编码器倍率、视觉 ROI 和控制参数仍不得写成已确认事实。

## 2. 规则优先级

发生冲突时按以下顺序处理：

1. 用户当前明确提出的要求；
2. `PROJECT_RULES.md` 中的项目硬规则；
3. `AI_DEVELOPMENT_GUIDE.md` 中的实现规范；
4. `PROJECT_ARCHITECTURE.md` 中的目录说明；
5. 现有代码惯例。

代码、Keil 工程配置和原理图用于确认当前事实。文档与代码不一致时，应先核查实际行为，
再同步修正文档，不能仅根据文件名推断。

## 3. AI 协作规则

1. 修改前阅读相关文档、代码、Keil 工程配置和硬件资源定义；
2. 用户只要求解释或诊断时，不擅自扩大为代码重构；
3. 用户明确要求实现功能时，可以完成代码修改和编译；只有明确包含烧录时才执行下载；
4. 不凭空假定协议、引脚、时钟、DMA 通道、设备方向、零点或标定参数；
5. 接入外设时说明资料来源、通信方式、初始化位置、数据路径和阻塞风险；
6. 修改后检查文件是否已经加入 Keil 工程，并执行与改动风险相称的验证；
7. 编译、烧录和硬件验证必须分别报告，不得用其中一项代替另外两项；
8. 发现架构文档过期时，在本次修改中同步更新；
9. 不确定的硬件现象必须标记为“待验证”，并给出安全的验证方法。

## 4. 分层与依赖方向

工程依赖只允许由上向下：

```text
App
  ↓
Drivers / Library
  ↓
BSP
  ↓
Core / STM32 HAL
```

### Core

- 保存 CubeMX/HAL 生成的启动、时钟、外设初始化和中断入口；
- `main.c` 只负责初始化和唯一主循环；
- 不放设备协议、应用任务、界面流程或控制策略；
- 重新生成 CubeMX 代码后，必须检查用户代码段和工程文件是否被覆盖。

### BSP

- 封装这块控制板上的 GPIO、ADC、SPI、UART、CAN、TIM、DMA 和中断资源；
- 负责字节、报文和硬件通道，不解释某个具体设备的业务含义；
- 可以提供阻塞接口，但持续运行的数据链路应优先提供中断或 DMA 接口；
- 不得包含 Driver、Service 或 Task 的头文件。

### Drivers

- 封装具体器件的初始化、协议解析、状态和设备能力；
- 通过 BSP 或经确认的官方 HAL 流程访问硬件；
- 不绘制应用界面，不根据任务编号改变行为；
- 同类设备存在多个实例时，优先使用“配置 + 实例”接口，避免散落的全局变量。

### Library

- 保存 PID、滤波、姿态解算、数据结构等纯软件能力；
- 不依赖 HAL、BSP、GPIO、LCD 或具体设备；
- 输入和输出应由参数表达，使算法可以在普通电脑上单独测试。

### App

- `App/System/`：上电流程、全局运行时、系统状态和安全处理；
- `App/Services/`：输入、事件、存储等多个任务共享的服务；
- `App/Comm/`：应用层通信协议和命令解释；
- `App/Tasks/`：菜单、任务注册和具体应用状态机。

禁止反向依赖。例如 BSP 不得调用 Task，Driver 不得调用应用 UI，Library 不得读取硬件。

## 5. 官方例程移植规则

1. 板载模块优先查找并遵循达妙官方对应例程；
2. LCD、KEY、BMI088、CAN/FDCAN、UART、PWM 等已验证底层流程不得无依据重写；
3. 使用到的官方源码必须复制到本工程内部，不得通过绝对路径引用外部例程；
4. 官方底层尽量保持原样，框架通过 BSP 或 Driver 建立稳定接口；
5. 偏离官方例程时，必须记录改动位置、原因、影响和验证结果；
6. 不为了目录形式整齐而破坏已经验证的寄存器、时序、DMA 或中断流程。

## 6. 协作式调度规则

本框架当前采用裸机协作式调度，只有 `Core/Src/main.c` 拥有无限循环：

```c
while (1)
{
    uint32_t now = HAL_GetTick();

    AppRuntime_Tick(now);
    InputService_Poll();
    TaskManager_Tick(now);
}
```

- `AppRuntime_Tick` 维护与具体任务无关的周期功能；
- `InputService_Poll` 统一扫描输入并生成事件；
- `TaskManager_Tick` 维护菜单或推进当前任务一步；
- 每次调用都必须在可预期的短时间内返回；
- 禁止在任务和服务中新增 `while (1)`、`for (;;)` 或长时间 `HAL_Delay()`；
- 周期动作使用 `now_ms` 与上次时间的无符号差值判断。

## 7. 任务接口规则

所有应用任务实现统一生命周期：

```text
Enter（进入一次） → Tick（重复调用） → Exit（退出一次）
```

- `Enter` 重置全部任务状态、申请或启动资源、建立初始输出；
- `Tick` 处理一个输入事件并推进一小步，不阻塞等待流程完成；
- `Exit` 停止本任务拥有的设备、DMA、PWM 或输出，并释放资源；
- 多阶段流程使用显式状态机，不用延时串联动作；
- Task3 当前用于五向按键 ADC 诊断，Task4～Task5 用于定位、视觉或底盘联调，Task6 用于松甲四轮台架测试；
- 需要改变任务数量或注册方式时，统一修改任务注册表，不能另建第二套选择逻辑。

## 8. 输入与通信规则

- 按键底层只由输入服务扫描，任务只接收统一的 `InputEvent_t`；
- 五向按键必须沿用 QDcan 已验证映射：`key_sw6=上`、`key_sw5=下`、`key_sw3=左`、
  `key_sw4=右`、`key_sw2=中键`，不得根据 ADC 驱动中的方向变量名重新推断；
- DMstm32 当前实测 ADC 中心值为：静止 `3588`、下 `736`、上 `1470`、左 `2188`、
  右 `2880`、中键 `1`。校准区间在 `InputService_ApplyAdcCalibration()` 中统一维护，
  区间之间必须保留死区，禁止重新使用未覆盖上键和左键实测值的旧窄阈值；
- 菜单中上/下用于选择、右键进入；左键只在任务运行时退出并触发安全停机；
- 任务不得重新初始化按键、替换底层回调或直接争用 ADC 状态；
- UART/CAN 中断只接收数据、记录位置或置事件，不直接执行应用流程；
- 应用通信必须校验帧头、长度、校验值、命令范围和数据新鲜度；
- 协议解析应放在 Driver 或 App/Comm，不能堆在中断入口或 `main.c`。

## 9. 中断、DMA 与实时性

- 中断中只做清标志、少量数据搬运、记录时间或通知上层；
- DMA 只负责搬运数据，完整帧解析在主循环中增量完成；
- 每次解析应设置处理预算，防止积压数据一次占满主循环；
- 显示、日志和存储操作必须限频，不能阻塞高频采集或控制；
- 周期模块应明确目标周期，并监测数据新鲜度、超时和最坏执行时间；
- `HAL_GetTick()` 的周期判断统一使用无符号减法，以兼容计数回绕。

## 10. 硬件资源与安全

- 新模块接入前检查引脚、定时器通道、DMA、IRQ、总线地址和带宽是否冲突；
- 共享资源必须有明确所有者，并在任务切换时按顺序停止、释放和重新配置；
- 输出设备应设置范围限制、变化率限制、通信超时和明确的安全默认值；
- 未确认的方向、零点、比例和反馈单位不能作为固定常量直接用于高输出测试；
- 首次验证应断开负载或降低输出，从零命令开始逐步增加；
- 退出任务、反馈超时、设备离线或状态异常时，应恢复安全输出；
- 当前 `PA0 / TIM2_CH1` 被多个示例驱动复用，未经资源重新分配不能同时启用。

## 11. 可移植性与配置

- 板级句柄、引脚和通道放在 BSP 或设备配置中，不散落在 Task；
- 设备 ID、采样周期、显示周期和容量限制使用具名配置，不使用意义不明的常数；
- 应用任务不得依赖某台设备的机械结构或固定装配方式；
- 台架专用参数应标明“测试配置”，不得写成实车已验证参数；
- 新增源码后同步维护 Keil 分组、包含路径和构建脚本；
- 删除或移动文件前检查工程引用，确保整体工程仍可独立构建。

## 12. 编译、烧录与验证

- Keil 工程：`MDK-ARM/CtrBoard-H7_FDCAN.uvprojx`；
- 推荐使用 VS Code 任务 `Keil: Build` 和 `Keil: Build + Flash`；
- 只有构建日志出现 `0 Error(s)` 才算编译成功；
- 只有下载日志确认 Program 与 Verify 成功才算烧录成功；
- 没有观察设备行为或采集验证数据，不能声称硬件功能已经验证；
- 编译失败时不得烧录旧产物冒充本次固件；
- 修改文档本身不需要重新编译固件。
